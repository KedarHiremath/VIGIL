# VIGIL Layer 1 — Evidence and Interpretation Schema Specification

**Status:** Initial implementation specification  
**Scope:** Provenance, Observation, Entity, Event, EventLink and EvidenceAssessment

## 1. Provenance

**Python file:** `src/vigil/domain/provenance.py`

| Attribute | Type | Required | Description |
|---|---|---|---|
| `producer_type` | Literal | Yes | Category of the model, tool, rule, agent or human that produced the result. |
| `producer_name` | `str` | Yes | Name of the producing component or person. |
| `producer_version` | `str \| None` | No | Version of the producing component, if known. |
| `method` | `str` | Yes | Operation or analysis method used to produce the result. |
| `input_artifact_ids` | `list[str]` | No | IDs of derived artifacts consumed during analysis. Defaults to an empty list. |

- References must not be blank or duplicated.

- Changes to fields, types, relationships or validation rules require corresponding tests and documentation updates.

# Investigation Management and Coverage Schemas

## 1. Purpose

This document defines the domain contracts for managing investigations, recording examination coverage, and producing structured reports in VIGIL.

The schemas build on the existing source/media and evidence schemas. They store references to existing objects rather than duplicating their contents.

## 2. Investigation

| `title` | `str` | Yes | Human-readable investigation title. |

| `scope_description` | `str` | Yes | Describes the investigation boundaries and constraints. |
| `media_asset_ids` | `list[str]` | No | IDs of media assets associated with the investigation. Defaults to an empty list. |
| `source_reference_ids` | `list[str]` | No | IDs of source references associated with the investigation. Defaults to an empty list. |
| `created_at` | `datetime` | No | Time the investigation record was created. Defaults to the current UTC time and must be timezone-aware. |
| `created_by` | `str \| None` | No | Optional identifier for the user or component that created the investigation. |

| Value | Meaning |
|---|---|
| `examined` | The examination was completed successfully. |
| `partial` | Only part of the intended examination was completed. |
| `failed` | The examination attempt failed. |
| `not_examined` | The source or interval has not been examined. |

### Attributes

| Attribute | Type | Required | Description |
|---|---|---|---|
| `coverage_id` | `str` | Yes | Unique identifier for this coverage record. |
| `investigation_id` | `str` | Yes | Identifier of the associated investigation. |
| `source_reference_id` | `str` | Yes | Identifier of the source being examined. |
| `status` | `CoverageStatus` | Yes | Outcome of the examination. |
| `interval_start` | `datetime \| None` | No | Start of the interval being examined. |
| `interval_end` | `datetime \| None` | No | End of the interval being examined. |
| `examined_at` | `datetime \| None` | No | Time the examination was recorded as completed or attempted. |
| `notes` | `str \| None` | No | Explanation of limitations, failures, or other relevant details. |

### Validation rules

- Required identifiers must not be blank.
- Supplied timestamps must be timezone-aware.
- `interval_start` and `interval_end` must either both be provided or both be omitted.
- The interval end cannot precede the interval start.
- `examined` status requires `examined_at`.
- Artifact IDs must be nonblank and unique.
- Optional notes cannot be blank when supplied.

### Interpretation rule

Coverage records describe examination activity. They do not establish that a source contains no relevant events. In particular, `not_examined` must not be interpreted as a successful examination with no findings.

## 5. Dependencies and boundaries

The schemas reference existing domain concepts:

- `Investigation` references media assets and source references.
- `CoverageRecord` references an investigation, a source reference, and optional artifacts.
- `Report` references an investigation, observations, events, evidence assessments, and coverage records.

These are identifier references, not automatic database relationships. Referential existence checks, persistence, and cross-record consistency are responsibilities of a later repository or application-service layer.

## 6. Intentionally deferred

The following are outside this schema set's current scope:

- Investigation lifecycle transitions.
- Automatic calculation of examination completeness.
- Rules for deciding whether coverage is sufficient.
- Report rendering to PDF, HTML, or other formats.
- Validation that every referenced ID exists in persistent storage.
- Report versioning and approval workflows.

These capabilities can be added when the corresponding application behavior is designed.

# VIGIL Shared Contracts and Validation Rules

## 1. Purpose

This document defines conventions that apply across VIGIL domain schemas and execution contracts. Individual schemas must follow these rules rather than independently defining the meaning of identifiers, timestamps, confidence values, references, provenance, and validation.

**Implementation status:** The shared primitive types are implemented in `src/vigil/domain/common.py`. The source/media, evidence, investigation-management, and orchestration schema groups have been migrated to these types, with unit tests covering their validation behavior. Cross-record existence checks, persistence guarantees, and workflow-level state transitions remain responsibilities of later layers.

## 2. ID conventions

### Decision

- Represent identifiers as nonblank strings.
- Use stable identifiers for persisted objects; an object's ID must not change when its descriptive fields change.
- Human-readable prefixes such as `media-`, `event-`, and `task-` may be used as a readability convention.
- A prefix is not a guarantee of uniqueness.
- Do not use list positions, display labels, timestamps, or mutable attributes as persistent identifiers.
- Do not assume IDs from different entity types are globally unique unless the storage layer explicitly guarantees this.

### Validation

`Identifier` is defined in `src/vigil/domain/common.py`. It strips surrounding whitespace and rejects blank values.

The mechanism that generates IDs and guarantees uniqueness in persistent storage is a responsibility of a later application or persistence layer.

## 3. Timestamp and interval conventions

### Real-world timestamps

- Use timezone-aware datetimes for real-world timestamps.
- Use UTC as the default timezone for timestamps generated by VIGIL.
- Preserve the distinction between when an event occurred and when VIGIL observed, processed, or recorded it.
- Unknown timestamps should remain unknown; do not substitute the current time for an unknown event time.
- Do not use naive datetimes to represent real-world time.

The reusable `Timestamp` type uses Pydantic's timezone-aware datetime validation.

### Media-relative time

A media offset is a position relative to a media asset, such as a number of seconds from the beginning of a video. It is not a real-world datetime.

When both a media-relative position and an estimated real-world time are required, represent them as separate fields and document their relationship.

### Interval boundaries

Use half-open intervals: `[start, end)`.

- The start is included.
- The end is excluded.
- The end must not precede the start.
- If both boundaries are required, both must be present.
- A zero-length interval is empty.
- Unknown boundaries should be represented explicitly as unknown where the schema permits them.

This convention allows adjacent intervals to meet at a boundary without overlapping.

## 4. Confidence and uncertainty

### Confidence

- A confidence score is numeric and normalized from `0.0` to `1.0`.
- The score must be finite.
- Confidence is optional when the producing component cannot justify a score.
- A score is not automatically a calibrated probability.
- The meaning of a score must be documented for the component or model that produces it.

The shared `ConfidenceScore` type validates the numeric range and rejects non-finite values.

### Uncertainty and evidence quality

Confidence, uncertainty, and evidence quality are related but distinct:

- **Confidence:** How strongly a component supports its own output.
- **Uncertainty:** What remains unknown, ambiguous, or unresolved.
- **Evidence quality:** How suitable the supporting evidence is for the relevant assessment.

Do not encode all three concepts in a single numeric field. Use explicit assessments and rationale where appropriate.

## 5. Reference rules

- Store identifiers when one schema refers to another object.
- Avoid copying the full referenced object into every dependent schema.
- Use consistent ID types for references and target objects.
- Reject blank reference IDs.
- Reject duplicate references when list membership represents a set of related objects.
- Do not assume that a syntactically valid ID points to an existing object.
- Check referential existence at the repository or application-service boundary, where related records can be looked up.

The shared `ReferenceIds` type validates nonblank, unique reference IDs.

Reference lists should retain ordering only when ordering has meaning to the domain. Otherwise, their meaning is membership rather than sequence.

## 6. Provenance rules

Provenance records how a result was produced and what it depends on.

Where applicable, retain:

- Producer type and name.
- Producer or model version.
- Processing or analysis method.
- Input artifact IDs.
- Parent observation IDs.
- Creation timestamp.
- Relevant transformation or derivation information.

Derived observations, artifacts, and events should retain links to their inputs. Correlation must not erase the distinction between an original source, a derived result, and an interpretation.

Provenance supports traceability but does not, by itself, prove that a result is correct.

## 7. Schema versioning

### Contract evolution

- Treat externally exchanged schemas as versioned contracts.
- Introduce an explicit schema version at a serialized message, API, or persisted-document boundary where compatibility must be managed.
- Do not add a redundant version field to every internal model without a concrete need.
- Prefer additive optional fields when they preserve existing semantics.
- Treat field removal, type changes, stricter validation, and changes in field meaning as potentially breaking changes.
- Document migration requirements before deploying breaking changes.
- Test compatibility between producers and consumers when a contract changes.

The initial contract baseline is version `1.0` for documentation and compatibility planning. This does not imply that every existing model currently carries a serialized `schema_version` field.

## 8. Validation rules

Validation should happen at multiple boundaries:

1. **Schema validation:** Types, required fields, nonblank IDs, confidence ranges, timezone-aware timestamps, and local interval rules.
2. **Cross-reference validation:** Whether referenced IDs exist and whether relationships between records are valid.
3. **Workflow validation:** Whether a task result or state transition is consistent with the workflow.
4. **Persistence validation:** Uniqueness, transaction consistency, and storage-level integrity.
5. **Semantic validation:** Whether a finding is adequately supported by evidence and whether uncertainty is accurately represented.

Do not attempt to solve every layer in a single Pydantic model. Keep each rule at the boundary that has enough information to enforce it correctly.

## 9. Shared implementation

Shared types are defined in:

`src/vigil/domain/common.py`

- `Identifier`: nonblank string identifier.
- `Timestamp`: timezone-aware datetime.
- `ConfidenceScore`: finite numeric score in the range from `0.0` to `1.0`.
- `ReferenceIds`: list of nonblank, unique reference identifiers.

New schemas should use these types where their semantics match. Existing schemas should be migrated incrementally, with tests confirming that their intended behavior remains unchanged.

### Initial schema migration: source and media

The source/media schema group uses the shared types as follows:

| Schema | Shared types applied |
|---|---|
| `Camera` | `Identifier` for `camera_id` |
| `MediaAsset` | `Identifier` for `media_asset_id` and optional `camera_id`; `Timestamp` for `recorded_at` |
| `SourceReference` | `Identifier` for `media_asset_id`; `Timestamp` for `source_timestamp` |
| `Artifact` | `Identifier` for `artifact_id`; `Timestamp` for `created_at` |

Domain-specific validation remains in each schema. Examples include IANA timezone validation, finite media positions, positive-length intervals, SHA-256 checksums, and artifact/media-type compatibility.

This migration does not verify that a referenced camera or media asset exists in persistent storage. Cross-record existence checks remain the responsibility of a future repository or application-service layer.

### Evidence schema migration

The evidence schemas use the shared types as follows:

| Schema | Shared types applied |
|---|---|
| `Provenance` | `Timestamp`, `ReferenceIds` |
| `Observation` | `Identifier`, `ConfidenceScore`, `ReferenceIds` |
| `Entity` | `Identifier`, `ReferenceIds` |
| `Event` | `Identifier`, `Timestamp`, `ReferenceIds` |
| `EventLink` | `Identifier`, `ConfidenceScore`, `Timestamp` |
| `EvidenceAssessment` | `Identifier`, `Timestamp` |

Domain-specific validation remains in place, including required supporting observations, event time ordering, distinct endpoints for event links, and finite entity attribute values.

Confidence values use the shared finite range from `0.0` to `1.0`. Reference lists use the shared validation rules for blank and duplicate IDs, while fields requiring at least one reference retain their minimum-length constraints.

The schemas validate the structure and syntax of references, but they do not verify that referenced records exist in persistent storage. Cross-record existence checks remain the responsibility of a repository or application-service layer.

## 10. Deferred implementation

The following are not fully implemented by this document or the shared types alone:

- Persistent ID generation and uniqueness guarantees.
- Automatic conversion between media-relative and real-world time.
- Referential existence checks across stored records.
- Provenance propagation through every processing stage.
- API or database migration tooling for schema versions.
- Cross-record and workflow-level validation.

These responsibilities should be implemented when the relevant repository, pipeline, and integration contracts are introduced.


### Investigation management and coverage migration

The investigation management schemas use the shared types as follows:

| Schema | Shared types applied |
|---|---|
| `Investigation` | `Identifier`, `Timestamp`, `ReferenceIds` |
| `CoverageRecord` | `Identifier`, `Timestamp`, `ReferenceIds` |
| `Report` | `Identifier`, `Timestamp`, `ReferenceIds` |

Domain-specific validation remains in place, including nonblank descriptive text, paired coverage interval endpoints, interval ordering, the requirement for an examination timestamp when coverage is marked as examined, and nonblank optional notes.

The shared `Identifier` and `ReferenceIds` types normalize surrounding whitespace and reject blank identifiers. Reference lists also reject duplicate identifiers after normalization. The shared `Timestamp` type requires timezone-aware datetime values.

The schemas validate the structure and syntax of references, but they do not verify that referenced records exist in persistent storage. Cross-record existence checks remain the responsibility of a repository or application-service layer.



### Execution and orchestration migration

The orchestration schemas use the shared types as follows:

| Schema | Shared types applied |
|---|---|
| `InvestigationState` | `Identifier`, `ReferenceIds`, `Timestamp` |
| `TaskRequest` | `Identifier`, `ReferenceIds`, `Timestamp` |
| `TaskResult` | `Identifier`, `ReferenceIds`, `Timestamp` |
| `ModelOutput` | `Identifier`, `ReferenceIds`, `Timestamp`, `ConfidenceScore` |

`ErrorDetail` retains its domain-specific validation for nonblank error text, finite retry delays, and retry-policy consistency.

The task and investigation state schemas retain their lifecycle rules, including required error details for failed tasks, prohibition of errors on completed tasks, terminal investigation timestamps, and chronological ordering of start and completion timestamps.

The shared contracts validate individual values and reference-list structure. They do not execute tasks, manage transitions over time, or verify the existence of referenced records. Those responsibilities belong to the orchestration service, scheduler, or repository layer.

# VIGIL Layer 1 — Source and Media Schema Specification

**Status:** Initial implementation specification  
**Scope:** Camera, MediaAsset, SourceReference and Artifact

## 1. Camera

**Python file:** `src/vigil/domain/camera.py`

| Attribute | Type | Required | Description |
|---|---|---|---|

| `name` | `str` | Yes | Human-readable camera name. |
| `location_label` | `str \| None` | No | Physical location of the camera, if known. |
| `timezone` | `str \| None` | No | IANA timezone associated with the camera, if known. |

**Validation rules**

- IDs and names must not be empty.
- Timezones must be valid IANA timezone names.
- Clock offsets must be finite numbers.
- Unknown metadata must remain explicitly optional.

## 2. MediaAsset

**Python file:** `src/vigil/domain/media_asset.py`

| Attribute | Type | Required | Description |
|---|---|---|---|
| `media_asset_id` | `str` | Yes | Stable unique identifier for the original media. |

| `storage_uri` | `str` | Yes | Location or storage key for the original media. |
| `camera_id` | `str \| None` | No | Identifier of the producing camera, if known. |
| `duration_seconds` | `float \| None` | No | Positive duration in seconds, if applicable and known. |
| `recorded_at` | `datetime \| None` | No | Timezone-aware wall-clock time corresponding to the recording's beginning. |
| `sha256` | `str \| None` | No | SHA-256 checksum of the original media, when available. |

**Validation rules**

- IDs and storage references must not be empty.
- Media type must be one of the declared values.
- Duration must be positive and finite when supplied.
- Recording timestamps must be timezone-aware.
- SHA-256 checksums must contain exactly 64 hexadecimal characters.
- The referenced camera must exist when `camera_id` is supplied.

## 3. SourceReference

**Python file:** `src/vigil/domain/source_reference.py`

| Attribute | Type | Required | Description |
|---|---|---|---|
| `media_asset_id` | `str` | Yes | Identifier of the original media containing the evidence. |
| `start_seconds` | `float` | Yes | Inclusive start position in seconds on the original media timeline. |
| `end_seconds` | `float` | Yes | Exclusive end position in seconds on the original media timeline. |
| `source_timestamp` | `datetime \| None` | No | Timezone-aware wall-clock timestamp corresponding to `start_seconds`, when known. |

**Validation rules**

- Media IDs must not be empty.
- Timeline positions must be finite and non-negative.
- `end_seconds` must be strictly greater than `start_seconds`.
- Wall-clock timestamps must be timezone-aware.
- When media duration is known, the interval must not extend beyond it.
- Source references must resolve to existing media assets.

## 4. Artifact

**Python file:** `src/vigil/domain/artifact.py`

| Attribute | Type | Required | Description |
|---|---|---|---|
| `artifact_id` | `str` | Yes | Stable unique identifier for the derived artifact. |
| `artifact_type` | `frame \| crop \| clip \| audio_segment \| derived_media` | Yes | Kind of derived media. |
| `media_type` | `video \| audio \| image` | Yes | Actual media type of the stored artifact. |
| `storage_uri` | `str` | Yes | Location of the derived media. |
| `source_reference` | `SourceReference` | Yes | Original media and timeline interval from which the artifact was derived. |
| `sha256` | `str \| None` | No | SHA-256 checksum of the derived artifact, when available. |
| `created_at` | `datetime` | Yes | Timezone-aware timestamp when the artifact was created; defaults to UTC now. |

**Validation rules**

- Artifact IDs and storage references must not be empty.
- `frame` and `crop` require image media.
- `clip` requires video media.
- `audio_segment` requires audio media.
- `derived_media` may represent any declared media type.
- Creation timestamps must be timezone-aware.
- Checksums must contain exactly 64 hexadecimal characters when supplied.
- Source references must resolve to existing media assets.
- The source interval must be valid for the referenced media.

## Shared conventions

- IDs are opaque, non-empty strings; their generation mechanism is not specified by these schemas.
- Media-relative times are expressed in seconds.
- Source intervals use the half-open convention `[start_seconds, end_seconds)`.
- Wall-clock timestamps must include timezone information.
- Unknown information is represented with optional fields, not fabricated defaults.
- Cross-record relationships must be checked by the repository or service layer.
- Schema changes must be accompanied by tests and documentation updates.
