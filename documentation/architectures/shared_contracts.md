# VIGIL Shared Contracts and Validation Rules

## 1. Purpose

This document defines conventions that apply across VIGIL domain schemas and execution contracts. Individual schemas must follow these rules rather than independently defining the meaning of identifiers, timestamps, confidence values, references, provenance, and validation.

**Implementation status:** These conventions are the agreed target contract. The shared primitive types are implemented in `src/vigil/domain/common.py`. Existing schemas may still contain local validation logic and should be migrated to the shared types in a controlled pass.

## 2. ID conventions

### Decision

- Represent identifiers as nonblank strings.
- Use stable identifiers for persisted objects; an object's ID must not change when its descriptive fields change.
- Human-readable prefixes such as `media-`, `event-`, and `task-` may be used as a readability convention.
- A prefix is not a guarantee of uniqueness.
- Do not use list positions, display labels, timestamps, or mutable attributes as persistent identifiers.
- Do not assume IDs from different entity types are globally unique unless the storage layer explicitly guarantees this.

### Validation

`Identifier` is defined in `src/vigil/domain/common.py`. It strips surrounding whitespace and rejects blank values.

The mechanism that generates IDs and guarantees uniqueness in persistent storage is a responsibility of a later application or persistence layer.

## 3. Timestamp and interval conventions

### Real-world timestamps

- Use timezone-aware datetimes for real-world timestamps.
- Use UTC as the default timezone for timestamps generated by VIGIL.
- Preserve the distinction between when an event occurred and when VIGIL observed, processed, or recorded it.
- Unknown timestamps should remain unknown; do not substitute the current time for an unknown event time.
- Do not use naive datetimes to represent real-world time.

The reusable `Timestamp` type uses Pydantic's timezone-aware datetime validation.

### Media-relative time

A media offset is a position relative to a media asset, such as a number of seconds from the beginning of a video. It is not a real-world datetime.

When both a media-relative position and an estimated real-world time are required, represent them as separate fields and document their relationship.

### Interval boundaries

Use half-open intervals: `[start, end)`.

- The start is included.
- The end is excluded.
- The end must not precede the start.
- If both boundaries are required, both must be present.
- A zero-length interval is empty.
- Unknown boundaries should be represented explicitly as unknown where the schema permits them.

This convention allows adjacent intervals to meet at a boundary without overlapping.

## 4. Confidence and uncertainty

### Confidence

- A confidence score is numeric and normalized from `0.0` to `1.0`.
- The score must be finite.
- Confidence is optional when the producing component cannot justify a score.
- A score is not automatically a calibrated probability.
- The meaning of a score must be documented for the component or model that produces it.

The shared `ConfidenceScore` type validates the numeric range and rejects non-finite values.

### Uncertainty and evidence quality

Confidence, uncertainty, and evidence quality are related but distinct:

- **Confidence:** How strongly a component supports its own output.
- **Uncertainty:** What remains unknown, ambiguous, or unresolved.
- **Evidence quality:** How suitable the supporting evidence is for the relevant assessment.

Do not encode all three concepts in a single numeric field. Use explicit assessments and rationale where appropriate.

## 5. Reference rules

- Store identifiers when one schema refers to another object.
- Avoid copying the full referenced object into every dependent schema.
- Use consistent ID types for references and target objects.
- Reject blank reference IDs.
- Reject duplicate references when list membership represents a set of related objects.
- Do not assume that a syntactically valid ID points to an existing object.
- Check referential existence at the repository or application-service boundary, where related records can be looked up.

The shared `ReferenceIds` type validates nonblank, unique reference IDs.

Reference lists should retain ordering only when ordering has meaning to the domain. Otherwise, their meaning is membership rather than sequence.

## 6. Provenance rules

Provenance records how a result was produced and what it depends on.

Where applicable, retain:

- Producer type and name.
- Producer or model version.
- Processing or analysis method.
- Input artifact IDs.
- Parent observation IDs.
- Creation timestamp.
- Relevant transformation or derivation information.

Derived observations, artifacts, and events should retain links to their inputs. Correlation must not erase the distinction between an original source, a derived result, and an interpretation.

Provenance supports traceability but does not, by itself, prove that a result is correct.

## 7. Schema versioning

### Contract evolution

- Treat externally exchanged schemas as versioned contracts.
- Introduce an explicit schema version at a serialized message, API, or persisted-document boundary where compatibility must be managed.
- Do not add a redundant version field to every internal model without a concrete need.
- Prefer additive optional fields when they preserve existing semantics.
- Treat field removal, type changes, stricter validation, and changes in field meaning as potentially breaking changes.
- Document migration requirements before deploying breaking changes.
- Test compatibility between producers and consumers when a contract changes.

The initial contract baseline is version `1.0` for documentation and compatibility planning. This does not imply that every existing model currently carries a serialized `schema_version` field.

## 8. Validation rules

Validation should happen at multiple boundaries:

1. **Schema validation:** Types, required fields, nonblank IDs, confidence ranges, timezone-aware timestamps, and local interval rules.
2. **Cross-reference validation:** Whether referenced IDs exist and whether relationships between records are valid.
3. **Workflow validation:** Whether a task result or state transition is consistent with the workflow.
4. **Persistence validation:** Uniqueness, transaction consistency, and storage-level integrity.
5. **Semantic validation:** Whether a finding is adequately supported by evidence and whether uncertainty is accurately represented.

Do not attempt to solve every layer in a single Pydantic model. Keep each rule at the boundary that has enough information to enforce it correctly.

## 9. Shared implementation

Shared types are defined in:

`src/vigil/domain/common.py`

- `Identifier`: nonblank string identifier.
- `Timestamp`: timezone-aware datetime.
- `ConfidenceScore`: finite numeric score in the range from `0.0` to `1.0`.
- `ReferenceIds`: list of nonblank, unique reference identifiers.

New schemas should use these types where their semantics match. Existing schemas should be migrated incrementally, with tests confirming that their intended behavior remains unchanged.

## 10. Deferred implementation

The following are not fully implemented by this document or the shared types alone:

- Persistent ID generation and uniqueness guarantees.
- Automatic conversion between media-relative and real-world time.
- Referential existence checks across stored records.
- Provenance propagation through every processing stage.
- API or database migration tooling for schema versions.
- Cross-record and workflow-level validation.

These responsibilities should be implemented when the relevant repository, pipeline, and integration contracts are introduced.
